# ADR-024: Opaque Native Folder Membership Resolves Legacy Composite-Key Ambiguity

> Authored directly in the routed tree on 2026-08-22; the index carries only the keyword-bearing summary.

> **2026-09-11 amendment (hotfix 1.7.7):** inventory ABSENCE is not deletion evidence unless the row's ACCOUNT is present in that inventory. `browser.accounts.list(true)` returns what Thunderbird has LOADED so far, not what exists; on a cold start it can omit whole accounts for many minutes. On 2026-09-10 the membership state pass and the orphan sweep removed ~58k native rows (entire archive trees) because their owner `folderId` was absent from a partial inventory. Both removal sites now keep any row whose `accountId` (the `msgId` prefix before the first `:`) is not among the inventory's account ids (`_folderReconTrustedAccountIds`); telemetry `unloadedAccountRowsKept`. **1.7.8:** the rule also covers the legacy (non-capable helper) recheck branch of the orphan sweep, which reached removal through a global query that cannot see unloaded accounts. This is the account-liveness guard the legacy `_reconcileCleanupStaleEntries` always had (`ensureAccountChecked`) and the ADR-024 port dropped (MIS-018 ×19). Accepted fail-closed cost: rows of a genuinely removed account stay until an explicit repair scan. "Empty inventory still cleans orphans" (ADR-022) is REVOKED — an empty inventory removes nothing.

> **2026-10-02 amendment (memo storage churn + state-pass convergence, branch `agent/tb-recon-storage-churn`):** the global membership-state pass and exact cutover are now VOLATILE process state, bound to the native connection generation and capability. Only the inventory digest/version/count and the per-folder completion set stay durable in `fts_folder_recon_memo`. Previously every 50-row state page rewrote the whole memo (~57 KiB): `_reconStorageTransaction` clones it, and Thunderbird keeps old and new copies for `storage.onChanged`, which amounted to ~1.25 GiB of churn on a large profile. The persisted pass authorised nothing, since session start re-earned cutover from page one anyway. A capable helper without a readable connection generation is treated as legacy (fail closed).
>
> The pass is drift-tolerant. It certifies property **P**: every native row has a non-null owner that structurally prefixes its raw `msgId`, and that owner is in the inventory or belongs to an account that is not loaded. It no longer requires one unchanged membership epoch across all pages, so it converges while new mail is indexed. Writers preserve P: `buildBatchHeader` is the single derivation site, the capable adapter refuses ownerless rows, and native writes never reassign an owner.
>
> - **Removal fence.** Stale-owner removal is fenced on `inventoryMembershipEpoch`, read immediately BEFORE the tick's inventory snapshot. Otherwise a row indexed into a folder created after the snapshot would look orphaned.
> - **Retries.** A lost fence, or a remove/assign failure, retries the same page. The sticky `passMutated` bit forces a replay pass.
> - **Publishing.** Cutover publishes only while the same pass, binding and connection generation are still current. The binding includes a topology serial that every `folders.*`/`accounts.*` event bumps synchronously, read before the inventory snapshot, so a pass judged against an inventory a rename/move/delete has since overtaken never publishes cutover.
> - **Per-operation mode.** Exact or legacy membership is captured ONCE when a folder reconcile or orphan-sweep operation starts and is never re-decided after an `await`. A reconnect mid-operation cannot switch an in-flight operation to legacy key ranges, which on a `F` / `F:suffix` pair would read a child folder's rows as the parent's and remove them.
> - **Telemetry.** Flat aggregate counters only: `membershipStatePages`, `membershipStatePageRetries`, `membershipStateRestart{MutatedReplay,UnresolvedReplay,Revoked,BindingChanged,PageInvalid}`, `membershipCutovers`, `membershipLastPassSlices` (`membershipInventoryResets` removed 2026-10-04 with the eager scan).

> **2026-10-03 amendment (reconciliation defect fixes, branch `agent/tb-recon-pr2-narrow`):** ownerless rows, unloaded accounts and orphan completion.
>
> - **Total ownerless-row classifier.** `_resolveFolderMembershipAssignment` returns exactly one of `assign`, `ghost`, `unloaded` or `unresolved` for every NULL-owner row, so a row whose message is gone is no longer replayed forever. An untrusted-account row is `unloaded` with no query. A key with no inventory candidate is a `ghost` (exact state pass only). Otherwise each candidate gets the folder-scoped `messages.query` first, and a scoped POSITIVE is conclusive ownership *(2026-10-04: the scoped check is the folder's msgDB Message-ID probe — see "The scoped check is a msgDB index probe" below)*. Only a candidate whose scoped query was negative or threw gets one global `recheckMessageInFolder`. One present owner assigns; two owners, or any `"error"`, is `unresolved`; every candidate globally absent is a `ghost`. No-separator keys are `unresolved`. Empty-path and root-path keys are historical only: `buildBatchHeader` cannot produce one, and a stray one is removed as zero-candidate.
> - **Budget and cursor.** The slice checks `rechecksPerSlice` before a row's FIRST global query and then finishes the row, so a slice issues at most `rechecksPerSlice + k − 1` global queries (k = that row's candidates) and always makes progress. Classification is row-atomic. The pass cursor advances only past fully classified rows. Fenced ghost removal and read-back come before the unfenced assignments *(reversed 2026-10-04: the page's assignments commit first, so a withheld removal never costs them)*; a removal sets `passMutated`, which forces one page-only replay before cutover. `unresolved` rows force a replay after the terminal page but never pin the cursor. **A `done:true` page is terminal only after its last row is processed: an interrupted terminal page grants no cutover, no orphan completion and no marker clear.** No NULL→revoke site remains; the trust test happens in the classifier.
> - **Unloaded accounts.** Untrusted-account rows, NULL or owned, are kept and counted in `pass.unloaded` (the legacy walk's `unloadedAccountRowsKept`); they do not count as unresolved, and cutover may be proven with them present. The pending marker is cleared only after a completed pass with `unloaded === 0`. When only unloaded rows remain, the scheduler wakes itself with `inventory_retry` after `min(errorDelayMs·2ⁿ, 6 h)`, where n counts consecutive unloaded-terminal passes and resets when the inventory digest changes. **A late-loading account is therefore re-inventoried within at most 6 h even with no other wake.** A genuinely deleted account keeps its rows and the marker, and the startup pass runs each session (owner-accepted).
> - **Orphan completion ≡ complete ∧ bound, in both modes.** There is no epoch-equality clause and no `terminalEpoch`. Previously one drain `indexBatch` after completion looped `orphan_continue` with the marker never clearing. Exact mode: orphan completion IS the completed, bound membership-state pass. The separate exact orphan sweep is deleted. A late `index_batch` that commits after the pass leaves a stale extra row until the next session (owner-accepted, issue #111). Legacy mode: see the ADR-022 2026-10-03 amendment.
> - **A removal and a re-add never cross.** A ghost or stale-owner removal is withheld (same-page retry) when any message add/remove event arrived after its page's classification began (`_folderReconMutationSerial`, bumped synchronously by every event). The incremental drain's "already indexed?" decision (`filterNewMessages` plus its existence verify) runs under the membership mutex (`runFtsMembershipRead`), so it waits out an in-flight removal instead of dequeuing a re-add against a row that removal is about to delete. Ordering is enforced where the two writers meet; no downstream repair is relied on for this race.
> - **Legacy outside-prefix keys.** A trusted-account key outside every inventory prefix keeps the live, budgeted global `recheckMessageInFolder` before removal. A confirmation-free removal is unsafe: a folder renamed back while the page is read bumps the topology serial but not the membership epoch, so the fence would admit the removal, and a later overlap refusal would leave the row missing.

> **2026-10-03 amendment (branch `agent/tb-recon-pr2b-fast-check`):** identity-gated UID tier, one removal guard, released scoped lists.
>
> - **UID-only tier requires the msgDB token in exact mode.** The stored Message-ID projection is reused only on the msgDB incarnation that earned it (see the ADR-022 2026-10-03 PR 2b amendment); a missing or different token takes the full projection.
> - **One guard for removal vs re-add.** The private event-serial snapshot in the membership-state pass is deleted. The slice's lease assertion already rejects any message event since the slice began (the message-event serial `_folderReconMutationSerial`, not `_lastSyncEventMs`: two events can share a millisecond), and it runs before the fenced removal mutator, so a removal judged before a re-add event is never committed. *(Superseded 2026-10-04: the slice-wide veto livelocked the pass under unrelated mail — see row-scoped event evidence below.)* An event before the removal's fence is entered ends the slice as a same-page retry at pacing (`membershipStatePageRetries`). An event while the removal waits for the membership mutex fails the assertion inside the fence before the removal runs; the tick retries after the error delay, as the deleted guard's path also did. (Until the serial replaced the timestamp, an event in the same millisecond passed that assertion and the classified stale rows were removed; the re-added row was never among them.) The drain-side mutex ordering is unchanged.
> - **The per-folder stale direction is bound to the same serial.** `_folderReconStaleDirection` captures `_folderReconMutationSerial` at its start and asserts it with the lease after every await and inside the removal fence. A re-add delivered after an absence verdict queues the message but writes nothing native, so the membership epoch does not move; without the serial the fence admitted the removal of the now-live owned row (found in review, 2026-10-03).
> - **Scoped queries release their lists.** `_resolveFolderMembershipAssignment` releases any `MessageList` still open after its folder-scoped query on every exit (terminal page, failed continuation, interruption) through the shared `releaseMessageList` helper. *(Superseded 2026-10-04: classification opens no list — the scoped check is a msgDB index probe.)*

> **2026-10-03 amendment (PR 3):** membership fences read folder-scoped evidence (see the ADR-022 PR 3 amendment).
>
> - **Assignment fence.** *(Superseded 2026-10-04: the eager scan is deleted.)* A metadata-scan batch is fenced on its own folder (`[folder.folderId]`), not on every candidate of its keys; the assignment itself is still attributed to every registered candidate, and native ownership conflicts still fail the batch. A parent write outside a child's range no longer refuses the child's assignment.
> - **Stale-owner fence.** Ghost/stale-owner removal is fenced on the stale keys (a `{ msgIds }` read scope: any recorded change to a folder whose key range holds one of them, registered or not) since the pre-inventory epoch: an index into an unrelated folder no longer forces a same-page retry, while a row indexed into the deleted folder's path (a re-created folder, recorded through its explicit owner even before registration) still does.
> - **Completion persistence.** *(Superseded 2026-10-04: the eager scan is deleted.)* A folder's completed metadata scan is persisted under fences scoped to that folder.
> - **The eager metadata scan is deleted (2026-10-04).** The membership-state pass is the only migration stage and the only cutover proof: it assigns each ownerless row it meets (a scoped check of each candidate folder, global `recheckMessageInFolder` only on a negative) and alone earns cutover. The per-folder metadata scans that assigned owners in bulk ahead of it are gone, with their durable record (`folderMembershipMigration`: inventory digest and `completedFolderIds`, dropped from the memo on its next write) and the interim volatile scan backoff map. Before, the first incomplete folder's scan ran ahead of the state pass on every tick, so one newly inventoried folder with an unreadable msgDB blocked every folder's reconciliation (pre-existing since f06fb02). The interim backoff still let more failing folders than the 5-min cap ÷ `errorDelayMs` covers, or a busy folder invalidated between scan slices, hold the scheduler in migration forever. Cost: rows still ownerless (an unmigrated profile or a legacy helper's writes) are assigned with one msgDB Message-ID probe per candidate, bounded by the page size; only the global rechecks after a negative count against `rechecksPerSlice`. An unreadable folder's ownerless row still keeps cutover unearned (fail-closed); its owned rows need nothing, and after cutover it is reconciled with the per-folder backoff while healthy folders complete.
> - **Row-scoped event evidence (2026-10-04).** The state pass is no longer a global consumer of message events. An ownerless row's verdict reads only its candidate folders, so it is voided only by an event in one of them or the wildcard (`_folderReconLocalFoldersUnchangedSince`, taken before the row's first query); a voided row ends the page with the rows before it committed and the page retries (`membershipStatePageRetries`). Previously any message event anywhere voided the whole page, and mail drained into an unrelated folder inside every scoped query held the pass, cutover and every folder's repair behind it forever. The page's assignments commit before its removals (native only fills NULL, and a wrong owner is removed later as stale). A ghost or stale-owner removal is withheld (`stale_folder_remove_event`, same-page retry) by a `folders.*`/`accounts.*` event since the inventory snapshot (`_folderReconTopologySerial`) or by a local message event since that snapshot (serial read before the inventory) in any folder whose key prefixes a removed key, whether or not the inventory lists it (`_folderReconLocalKeysUnchangedSince`): a converted re-add in a folder that loaded after the snapshot, drained without a native write because the row already existed, keeps its row. The native fence's `{ msgIds }` scope covers re-owning writes. A page with removals commits its assignments inside that fence, passing its token, so the page's own owner writes are recorded with the fence's advance and never void its removal (assigning `/F`'s live row must not refuse the same page's `/F` ghost); only another writer's membership change since the inventory refuses the fence, before any of the page's assignments commit, and the whole page is re-read. A page with no removals assigns unfenced.
> - **Assignment commit check (2026-10-04).** A buffered assignment keeps its row's candidate scope and is re-checked synchronously immediately before its batch call; the first changed row cuts the page there (it and every later row, with their removals and counts, are re-read). Native NULL-only filling does not make an assignment from expired evidence right: a message moving between the readings of a colon-ambiguous key would otherwise commit the old owner, which a structural replay certifies. A change during the batch call itself marks the row's candidate folders' walks; the owner folder's stale direction removes a wrong owner and the true folder's missing direction re-adds the row.
> - **Pressure cuts the page, never discards it (2026-10-04).** Foreground pressure while an ownerless row is classified ends the page at that row like a voided row: the rows already classified are committed (assignments, removals, counts) and the cursor advances before the slice yields. The commit is checked against the reconcile lease only, never pressure, since the write is bounded by the page; pressure that rises during the commit itself is likewise honoured once the cursor has advanced. Before, pressure threw out of the slice with every verdict on the page dropped, so mail drained in any folder (which raises pressure) more often than a page's ~50 classifications starved the pass, cutover and every folder's repair; the deleted eager scan had kept its progress across pressure.
> - **The scoped check is a msgDB index probe (2026-10-04).** An ownerless row's candidate folder is checked with `tmMsgNotify.probeMessageIds` — the folder's msgDB Message-ID index (`getMsgHdrForMessageID`, a hashed Mork column lookup) — instead of a folder-scoped `messages.query`, which Thunderbird answers by walking every message in the folder: a migration of an M-message folder cost ~M² header visits. A clean present answer is the conclusive positive; a missing id, a probe error, an `uncertain` lookup (the per-id lookup threw) or an unreadable folder state falls to the global recheck as before. Each folder's URI is resolved once per slice. A positive read across an event in a candidate folder is voided by the commit-time row check, so no post-probe check is needed; the probe opens no `MessageList`.
> - **Owner-known writes are attributed to their owners alone (2026-10-04).** Native `index_batch` given a row's `folderId` and `assign_folder_membership_batch` change only that owner's membership: each fills a NULL owner or inserts a new row with it, and a different stored owner aborts the whole batch. So `ftsSearch.indexBatch` records only the rows' owners when the helper received them with their folderIds (`nativeFtsSearch.indexBatch` reports the shape it built for the receiving port in `wire.withFolderIds`; the scope is resolved after the call), and `assignFolderMembershipBatch` records only the named owners. Before, both also recorded every registered folder whose raw key range held a key, so mail drained into a prefix-named folder (`/Cold:Hot`) restarted the parent `/Cold`'s proofs on every arrival and a multi-page parent never completed under that traffic. An index sent in the legacy row shape (older helper, or a reconnect to one) changes key ranges and is still attributed by key, as is one never reported as sent. A key-only removal (`removeBatch`) cannot name the owner it deleted and is still recorded for every registered folder whose key range holds the key, so a removal in `/Cold:Hot` still restarts `/Cold`'s proof (bounded by the removals; authoritative removal attribution needs the helper to report the owners it deleted, deferred).

> **2026-10-04 amendment (PR 3b, branch `agent/tb-recon-pr3b`): exact folder repair no longer waits for global cleanup; state-pass evidence is key-scoped.** The text above is kept as history; where it says "cutover" gates folder work, read this amendment.
>
> - **Exact folder work needs only capability.** `_useExactFolderMembership` is a capable helper with a readable connection generation. Every folder reconciles through its exact owner listing from a session's first slice. The old cutover flag is renamed `_folderMembershipCleanupProven`; with `_folderMembershipCleanupComplete(binding)` (completed, bound, unexpired pass, `passUnresolved === 0`, no replay pending) it gates only the state pass's early return and orphan/session completion. Exact proofs are sound before cleanup completes: an ownerless or stale-owner row is in no inventory folder's owner listing, so it can only show a deficit, never a false equality. The exact UID tier stays identity-gated as before.
> - **Fair turns while cleanup is incomplete.** Ticks alternate a state-pass slice and a folder slice (volatile `_folderReconMembershipTurn`). A folder turn never reads a state page. A no-target folder turn runs the pass page, or inside the unresolved-retry window returns `unresolved_retry_wait` and arms the wake at min(replay deadline, earliest folder deferral, rolling wake). It never completes the session. A capability/connection change or generation retirement hands the next turn to the pass. Once cleanup is complete there is no alternation.
> - **In-session unresolved retry.** A terminal page with `passUnresolved > 0` restarts the pass (`unresolved_replay`) not before `membershipUnresolvedRetryMs` (10 min); folder turns run meanwhile. A rejected page mutation backs off exponentially from `errorDelayMs` to the generic failure cap; a new pass resets it.
> - **Affected-folder handoff.** Before a state-pass removal, and before a folder stale-direction removal of a key another inventory folder's prefix also holds (colon overlap), `_prepareFolderReconRemovalHandoff` revokes those folders' durable terminal-retry authorization (`partialPostVerify*`, `partialRetryNotBeforeMs`) in ONE storage transaction, written only when the memo shows that authorization. A failure commits nothing and the page retries. Its walk marks, and an assignment batch's owner walk marks, are issued before the native call is dispatched, so a committed mutation whose reply is lost still leaves each folder owed a walk.
> - **Key-scoped state-pass evidence** (supersedes the folder-scoped "Row-scoped event evidence", the `{ msgIds }` "Stale-owner fence" and the page cut in "Assignment commit check" above). A row's verdict depends only on its own raw key.
>   - Native: beside the folder ledger, `fts/operationCoordinator.js` records the exact keys every mutation attempted (`_membershipTouchedKeys`, LRU cap `changeLedgerKeyCap` 4096, own floor `_membershipKeyTouchFloor`), also on failure, partial commit and inside a fence. `fts/engine.js` always fills `scope.keys` (index rows, assignments, removals) while `msgIds` keeps its owner-only folder meaning. A mutation without keys raises the key floor; `clear` stays the wildcard. Predicate `ftsMembershipKeysUnchangedSince(keys, epoch)`; a fence scope `{ keys }` checks only those keys, the wildcard and the key floor.
>   - Local: `_noteFolderReconLocalChange(folderKey, rawKeys)` also records each event's raw key (`_folderReconLocalTouchedKeys`, cap `changeLedgerKeyCap`, own floor). Ingress is the tmMsgNotify callbacks (`_invalidateFolderReconProofForMessageEvent`, first statement, before any await), with the queue's raw-key shape formed inline and `<>` stripped. A folder event without a Message-ID voids every key its folder's range holds (`_folderReconLocalKeylessFolders`), and an event naming no folder stays the wildcard. `_tryAdmitPendingUpdate` records its key synchronously, admitted or high-water rejected. Predicate `_folderReconLocalExactKeyUnchangedSince`.
>   - Row-scoped refusal: an event on the row's own key, a native write that attempted it, or a key floor passing the verdict's baseline refuses ONLY that row. It gets no assignment and no removal, is counted unresolved (`membershipStateRowsRefused`), the cursor passes it, and the delayed replay re-classifies it. Page-wide refusals stay page-wide: lease/generation/connection loss, the topology serial, a wildcard local event, and at fence entry the native wildcard or key floor. Foreground pressure still commits the classified prefix.
>   - Removal: the fence scope is `{ keys: [] }`; inside it each ghost/stale key is kept only if `_folderReconLocalExactKeyUnchangedSince(key, inventoryLocalSerial)` and `ftsMembershipKeysUnchangedSince([key], inventoryMembershipEpoch)` hold. The baseline is still read before the inventory and never rebased. Narrowing the stale-owner fence from folders to keys is sound only because a re-created or renamed folder bumps `_folderReconTopologySerial` (a page-wide refusal) and the inventory is authoritative for "owner absent". Any change to the `folders.*`/`accounts.*` topology listeners touches this guarantee.
>   - Why: with folder scope, ordinary mail on other messages in a row's candidate folder voided its verdict and cut the page, so steady mail held the pass, cleanup and (before this unit) every folder's repair (probes, 2026-10-04).
> - **Owner-facing costs, not blessed:** (1) the first capable session of a profile with ownerless rows may sweep a folder visited before the pass reaches its rows. That costs about (such rows) / `missingPageKeys` memo writes, at most 2 visits, once per migration. (2) A permanently unresolvable ownerless row (two live colon-overlap owners) keeps cleanup incomplete: one full state pass per 10 min per session and no orphan/session completion. Folder repair is unaffected.
> - **Deleted in PR 3b:** the volatile pending flag and "pending marker" (completion is the orphan tail's quiet predicate `_folderReconQuietSince`); `_reconcileCleanupStaleEntries` (no production caller; the 2026-09-11 note above that names it is history); queue persistence (see ADR-022).

**Context:** The historical native primary key is the unchanged string `accountId:folderPath:Message-ID`. A same-account folder pair `F` / `F:suffix` makes legacy prefix ranges overlap, while RFC-valid Message-IDs may themselves contain colons (including IPv6 domain literals). Re-encoding every key would require a full reindex and would still tempt callers to infer delimiter ownership without live folder context.

**Decision:** Add an exact opaque app-owned `folderId` relation beside the unchanged raw `msgId`, following the shipped iOS relation-first design.

- The wire field remains named `folderId`, but its durable value is centrally derived as `tm-folder:v1:` plus `JSON.stringify([accountId, folderPath])` over the exact raw strings. JSON array/string escaping makes the ordered tuple injective without assigning delimiter ownership; the version prefix makes future formats explicit. No Unicode or percent normalization occurs, so colon, percent, non-BMP, and NFC/NFD-distinct paths remain distinct. The value is compared as opaque and is never decoded for Thunderbird APIs. Session-scoped `MailFolder.id` exists only beside the live inventory while calling WebExtension APIs and is never written to native or queue storage.
- Native hello advertises `capabilities.folderMembershipV1 === true`. Only then may fresh `indexBatch` rows carry a non-empty opaque `folderId`; a capable write missing it fails before RPC, while the adapter strips the additive field for older helpers. Each native-port generation owns two readiness promises: hello publishes that generation's capabilities, while operational readiness resolves only after its `init` succeeds. Internal Phase-A bootstrap is ordered `hello`, optional `updateCheck`/`updateRequest`, then `init`; every general external RPC awaits operational readiness and shapes from that same generation's hello result. The bootstrap retains its exact ready-state and port across every awaited update-manifest boundary, revalidates ownership before `init` or shared update/status writes, and a stale bootstrap cannot dispatch onto or mark unavailable its operational replacement. The one exception is a successful `updateRequest` response: native writes it and intentionally exits, so that response is the commit point; the old generation may disconnect before, during, or after banner UI without a stale error, receives no `init`, publishes no operational/available state, and its one disconnect schedules the replacement. Failure and no-update paths still require current-generation proof, and native failure `message` is authoritative with legacy `error` fallback. An owned asynchronous bootstrap failure rejects its gates and disconnects exactly its captured port before releasing ownership; synchronous connection failure has no port to close, and stale failure cannot close a newer port. Concurrent initialization coalesces onto one promise/port, and disconnect, failure, or reconnect invalidates both phases and host information without allowing a stale generation to resolve either. Rejected-bootstrap cleanup is keyed to the exact cached promise, so even a synchronous `connectNative()` throw permits a fresh retry and an older rejection cannot clear a newer generation. Thus an overlapping `indexBatch` cannot run before init or shape from stale pre-reconnect/pre-hello state.
- Exact reads use only bounded `listFolderMembership({folderId,afterMsgId?,limit?})` pages in BINARY `msgId` order; Thunderbird cooperatively streams the existing unsigned-64-length-framed SHA-256 across those pages without retaining a full native Message-ID list. Metadata backfill uses bounded `assignFolderMembershipBatch({assignments})` calls and the authoritative bounded global `listFolderMembershipState({afterMsgId?,limit?})` reader, whose entries carry `folderId:null|string`. Thunderbird does not depend on whether native stores this as a nullable column or a separate relation table, and there is no unbounded native fingerprint RPC.
- The startup scheduler performs at most one bounded opaque-membership native page per scheduler slice, including per-folder/global digest and orphan enumeration after cutover. An O(1) volatile cursor plus streaming SHA-256 state resumes the current proof; the scheduler releases normal ownership between pages, and capability/epoch/generation/folder mutation invalidation restarts safely from page one. There is no native/server session cache and crash/restart simply discards the volatile proof. It never fetches bodies and never performs a global reindex. Assignment calls are idempotent; `missing` means the message left the native index and is a normal accounted no-op, while conflicting non-empty ownership fails closed. Interruption discards only the live scan token and restarts that folder while already-written relation rows remain durable. Repeated bounded slices have no total-work cap.

  A per-folder stale page may reuse its initial native digest for a cursor or terminal comparison only if the membership epoch has not advanced. Removing a stale native row advances that epoch, so the current implementation restarts from a fresh proof on the next slice; this preserves correctness but can repeat earlier pages when many ghost rows are spread across a large folder.
- A durable inventory digest and per-folder completion set record metadata progress *(2026-10-04: the completion set is deleted with the eager scan; the state pass alone earns cutover)*. Exact-mode cutover is nevertheless session-local and is earned only after one beginning-to-end global membership-state pass is stable under a single membership epoch with no null/unresolved/conflicting row *(until 2026-10-04 also only after every current opaque folder's metadata scan had completed)*. A non-null owner absent from the fresh inventory is authoritative stale-folder evidence: its native row is removed under the same stable inventory/epoch fence and the global pass restarts. A current owner attached to a structurally mismatched raw key fails closed. A pass that assigns or removes anything is replayed from the beginning, and the volatile cutover bit is set only after its terminal durable marker succeeds. Capability downgrade or change clears every volatile scan/digest/session proof, so re-upgrade restarts the global pass at page one. Conflicts, ambiguous/absent live interpretations, folder-id inventory defects, storage uncertainty, pressure, or epoch drift leave migration incomplete.
- After cutover, per-folder equality/list/count and the orphan known-total use the opaque relation, so `F` and `F:suffix` are disjoint. An orphan row whose authoritative non-null owner is absent from the current inventory is removed directly without reparsing; current-owner mismatches still fail closed. The raw `msgId` remains the exact value hashed and returned. Helpers without the capability retain ADR-022/PR19's legacy overlap census and fail closed.
- Composite keys presented by tools, chips, queues, or exact-mode cleanup are resolved by enumerating live folder-prefix candidates and querying the candidate folder plus exact `headerMessageId`. Queue recovery may additionally use the persisted exact account/path captured from the authoritative enqueue header when it exactly prefixes the unchanged raw key; it explicitly strips legacy session `MailFolder.id` metadata. Its broad existence proof drains every continuation page, filters to that account, and authorizes deletion only after a complete successful target-account absence proof. Action-cache startup batches all structural candidates, lists each affected folder once through every continuation page, and treats folder interpretation—not message-row count—as the ambiguity boundary: exactly one matched folder applies the action to every unique same-folder WebExtension message row, including deduplicated continuation results; two matched folders fail closed. Structural prefix count alone is not ambiguity. Inbox tag checks likewise use current structured folder evidence instead of a manual second-colon split. Missing authoritative evidence, cross-account matches, or query uncertainty fail closed. The Message-ID tail is preserved byte-for-byte, including IPv6 literals. No context-free “last colon” codec is introduced.

**Rationale:** Folder membership is relational data already known at every fresh write. Storing that relation removes the need to decode an intrinsically non-injective display/search key, avoids a body/full-text rebuild, and lets the existing cooperative scheduler prove migration completion without blocking Thunderbird's main thread.

**Consequences:**

- The native helper and add-on must ship the additive wire contract together; old helpers remain safe but cannot reconcile overlapping folder ranges.
- A legacy row that cannot be assigned with unique live evidence deliberately prevents exact cutover until later mailbox evidence or repair resolves it.
- The raw key format and all existing search/result references remain compatible. Exact membership is an additive relation keyed by the app-owned durable tuple, not Thunderbird's session id and not a v2 global codec.
- Large profiles perform unbounded total metadata work through bounded calls and idle-duty scheduling. There is no one-time session cache of mailbox contents; only durable progress fields, one live bounded scan token, and O(1) volatile digest/cursor state exist.
- A historical true raw-`msgId` primary-key collision (two messages whose ambiguous folder/Message-ID components produce the exact same raw string) is not rewritten by this additive relation. Conflicting ownership is detected and remains fail-closed; eliminating that storage collision would require a separately designed key migration.

**Amendment (2026-10-05, removal owners):** `ftsSearch.removeBatch` attributes a removal to the owners the
helper reports (`removedFolderIds`, helper ≥ the folder-membership summary release) when the reply vouches
for every deleted row: `removedFolderIds` is an array of non-empty strings and `removedOwnerless` is `0`.
A removal in `/Cold:Hot` therefore no longer restarts `/Cold`'s proof. A legacy reply without the field, a
malformed field, any deleted ownerless row (the reply does not say which ids had none), and a failed or
timed-out call (owners unknown, not none) keep the conservative key-range attribution. Every attempted key
is still recorded in the key ledger, and the colon-overlap revocation before a removal is unchanged: owners
only narrow which proofs a committed removal restarts.
