# ADR-022: Cooperative UID/FTS Membership Reconciliation Replaces Count Inference and Automatic Scans

> Authored directly in the routed tree on 2026-08-13 rather than extracted from `DECISIONS.md`; the manifest's `sha256_preserved_block` is `-` and the index carries only the keyword-bearing summary.

> **2026-08-22:** [ADR-024](adr-024-opaque-native-folder-membership.md) resolves issue #20 for capable helpers by adding exact opaque folder membership beside the unchanged raw key. This ADR's overlap census remains the required fail-closed fallback for older helpers.

> **2026-09-11:** "empty inventories still clean orphans" is REVOKED by the ADR-024 amendment — a row is removable on inventory absence only when its account is present in the inventory; an empty or partial cold-start inventory removes nothing for the missing accounts.

> **2026-09-24:** For helpers with exact opaque membership, the one-native-page-per-slice budget in ADR-024 permits reuse of the initial terminal native digest after the fresh local verification scan only while the membership epoch remains unchanged. A stale removal or concurrent native write invalidates that digest and leaves the folder unverified for another bounded slice. The legacy helper path still takes a fresh terminal native fingerprint. This qualifies the "fresh native fingerprint" wording below; the accepted exact-mode proof is an epoch-fenced native fingerprint from earlier in the same slice.

> **2026-10-02:** Two changes to native-support evidence and wakes.
>
> - **Support evidence is per connection.** Native fingerprint support is cached per native connection generation, not per session. Only a protocol `Unknown (reader) method` answer latches "unsupported", and only for that connection. Any other probe failure (`native_probe_failed`) is retried by a scheduled turn with bounded exponential backoff (`errorDelayMs`·2ⁿ⁻¹, capped at `FOLDER_RECON_GENERIC_FAILURE_BACKOFF_MAX_MS`). The failure counter restarts on each new connection generation, so when every failed probe also triggers a reconnect attempt (itself rate-limited by the native reconnect cooldown) the effective retry cadence follows that cooldown rather than climbing to the cap. Either way the retry is bounded and never latches.
> - **Reconnect and topology wakes.** Every successful native operational init notifies `nativeFtsSearch.addConnectionListener`, which wakes reconciliation. `folders.onCreated/onDeleted/onRenamed/onMoved/onCopied` and `accounts.onCreated/onDeleted` re-arm the durable pending marker and wake the scheduler even after it went idle. Each event also marks the whole folder set dirty, so every folder is re-verified: a path swap or a remove/recreate leaves the final inventory identical, and every old native row still has a current owner, so only per-folder re-verification can see that contents moved. The dirty set is consumed only at the start of a tick and the marker clear refuses while it is non-empty, so an operation the event overtakes cannot keep its folder done. They are registered at module top level in `chat/background.js` (persistent events, primed on idle suspend). Correctness never depends on delivery: every event-page start runs reconciliation.
>
> The memo no longer receives per-state-page writes (see the ADR-024 2026-10-02 amendment).

> **2026-10-03 (branch `agent/tb-recon-pr2-narrow`):** legacy orphan stage, zero-write verified passes, and the train split.
>
> - **One-shot legacy basis.** The legacy orphan pass is bound to (indexer generation, inventory count/sha256, native connection generation, topology serial read before the inventory). Its basis reads `basisEpoch` first. It then counts each known folder's range with `countMsgIdRange`, `orphanBasisFoldersPerSlice` (new config key, 50) ranges per slice, continuing across slices without restarting. Then it reads the global count and calls `_assertFolderReconMembershipEpoch(basisEpoch)` through the membership mutex, which waits out an in-flight drain mutation. The folder ranges are disjoint, so under one epoch the folder counts sum to the global count exactly when no row lies outside every range. Equal counts mean the pass is complete. A mismatch or a lost epoch goes to the walk, never to a second basis for the same binding. A foreground-pressure interruption before the global count is in hand is not a failure: the next slice retries the count. A binding change starts a fresh pass. Previously the basis restarted on every epoch move, a livelock under mail flow.
> - **Fenced walk.** The walk is fenced on the inventory membership epoch captured before the inventory snapshot; a lost fence retries the same page. The terminal global-fingerprint safeguard is unchanged: drift replays from before-first. It is the only recovery for a late commit whose `indexBatch` was built before the pass. Completion means the terminal page was reached with no drift while the pass is still bound. The stored cursor `memo.orphanSweep` is deleted: it is ignored on read and removed on the next memo write.
> - **Overlap still refuses all orphan work.** While a legacy colon-overlap group exists, the no-target branch returns `ambiguous_folder_keyspace` before the orphan slice; the pass is neither run nor reset. Outside-prefix cleanup there stays starved with the marker held, as before. Progress there belongs to the next train unit, because it needs candidate-specific confirmation and a repair that reaches the overlapping folders' missing direction.
> - **Read-only passes write nothing.** A verified pass whose proof did not change makes zero `storage.local` writes. The round-robin folder cursor is volatile within a session and seeded from the memo; it is persisted only alongside a write that happens anyway, so after a restart it can lag by one folder. An unchanged full-projection checkpoint is compared field-by-field (all but `updatedAtMs`) and not rewritten; it still passes the generation/epoch guard and earns this session's verification. An outcome snapshot is written only when a non-read-only counter moved. A no-change startup performs exactly one marker set and one marker clear.
> - **Train split (owner, 2026-10-02).** This branch fixes defects only. The per-folder "nothing changed" fast check, the periodic re-verification deadline, the late-commit repair and the `_tryFallbackDeletion` scoped-negative sibling removal (unchanged here) belong to the next train unit. The exact NULL-row count RPC and the remaining memory suspects come after that.

> **2026-10-03 (branch `agent/tb-recon-pr2b-fast-check`):** startup walk, walk obligations, rolling re-walk, and storage-free pending state. A zero-enumeration "nothing changed" gate was built on this branch and then deleted (see the first bullet).
>
> - **No zero-enumeration certification (owner, 2026-10-03).** Every startup (new generation) verifies every exact-mode folder by enumeration: the UID-only tier when the msgDB incarnation token and UIDVALIDITY match the checkpoint, otherwise the full Message-ID projection. A stored verified checkpoint alone certifies nothing. The deleted gate compared token, UIDVALIDITY, HIGHESTMODSEQ, `numMessages`, offline activity and a raw native range sample. Review reproduced a permanent miss through it: Thunderbird stores the server's HIGHESTMODSEQ at SELECT (`nsImapMailFolder::UpdateImapMailboxInfo`) before it applies the downloaded headers (`NormalEndHeaderParseStream`), so HIGHESTMODSEQ plus count is server progress, not evidence of what the msgDB applied, and a count-preserving add/expunge with missed or abandoned events passed every condition forever. No Thunderbird-maintained local revision exists either: `nsDBFolderInfo` `highWaterKey` moves only on a new maximum key. CONDSTORE stays off: with CONDSTORE and no IDLE (TabMail's `mail.check_all_imap_folders_for_new` polling) other-client expunges leave ghost headers (Bugzilla 1123094, 1124569). Obsolete stored gate fields are ignored and dropped on an ordinary checkpoint rewrite; there is no migration scan.
> - **Experiment contract.** `tmMsgNotify.getFolderState(accountId, folderPath, options?)` keeps the base fields and adds `incarnationToken`, a msgDB char property (`tmFolderIncarnation`). With `{ensureIncarnationToken: true}` an empty token is created once (`Services.uuid`, braces stripped) and never overwritten; a failed write leaves it empty. The reconcile inventory read passes the option in exact mode, so the token exists before any proof that stores it. Every certifying checkpoint stores the token the closing read confirmed.
> - **The token is identity, not change evidence.** A missing or different token forces the full projection; the UID-only tier never reuses a stored projection across a msgDB swap with coincident UIDs. The UID-only hit's closing `getFolderState` read must show the same token AND the same UIDVALIDITY as the opening read.
> - **UID-only tier order (cost).** The bounded, resumable native digest completes first, then one fresh UID enumeration, then the closing identity read and the final epoch and event checks. The stamp captured at the first native page stays binding through the UID scan and the closing read. Before this, the UID scan ran again for every native page.
> - **Walk obligations.** `_folderReconDirty` is `Map<folderKey, markSerial>`, the single record of an owed walk. A mark removes the folder's session completion and working proof once, when produced; it clears the folder's deferral and failure count only when it is newer than the failure. The obligation is discharged only when an enumerating proof certifies the folder in an attempt that started at or after the mark (the attempt's mark serial is captured at its start and carried across page, pressure and budget yields), so a mark made during an attempt forces a later one. Pending cannot clear while any entry remains. Marking all folders expands, at mark time, to the known folders (last inventory, completed folders, folders with a next walk); a mark for any other key records nothing, because that folder is not completed and is walked once an inventory lists it, so marks produced while pressure keeps the inventory slice from running cannot grow the map. Producers: queue abandonment (manual clear, `queue_stuck`, overflow, unindexable), drain failure fairness, topology and exclusive-membership invalidation, a message event whose change could not be queued (that folder; an event that names no folder is left to the rolling walk, and an oversized restored queue's tail to the startup walk, which already covers every folder), reconnect, and the rolling tick.
> - **Reconnect re-walk.** At the capable-connection transition (new connection generation on a membership-capable helper), every known folder is marked, independently of the exact-mode predicate, which is already false for the new generation at that moment. The marks are serviced once migration re-earns cutover. Capability loss then regain marks again at the regain. (The 2026-10-02 note that reconnect re-verifies every folder was true only of the wake; the folders stayed completed.)
> - **Rolling re-walk (backstop, owner 2026-10-03).** `walkPeriodMs` (24 h) and the tick `reverifyIntervalMs` (20 min). Each certification sets the folder's next walk to one period later, except the first in a generation, which lands at a stable offset into the period (FNV-1a with the murmur3 finalizer; FNV-1a alone clusters keys that differ only in a suffix). The tick is volatile, armed by the first exact-mode tick of a generation, consumed only under the reconcile lease, and marks EVERY completed folder whose next walk is due. There is no per-tick cap: a cap made coinciding deadlines (clustered offsets, or a cohort a signal re-walked at once) wait for hours. The offsets only spread load (worst tick about twice the even share). A folder with outstanding work is never re-marked by the tick, because a mark newer than its running attempt would keep that attempt from ever discharging. Bound: a folder's next walk begins within `walkPeriodMs + reverifyIntervalMs` of its previous one, plus pass time and foreground pressure. No storage writes. The tick stays armed in exact mode, so an account that loads later without an account event is discovered.
> - **Blessed residual (owner, 2026-10-03).** An in-session local msgDB change that reaches no signal (IMAPDeleted/Expunged flag flips under the non-default "mark as deleted" model, Repair Folder, compaction rekey, an in-session UIDVALIDITY reset, extraction failures for an unknown folder, a message event that names no folder, a stale removal racing such a flip) and a native write that commits after its RPC timed out are repaired by the folder's next rolling walk, a reconnect re-walk, or the next startup. The helper's reader and writer queues are separate, so no later read proves a timed-out write settled. A late write for a folder that has since left the inventory is visited by no folder walk, so a completed membership-state pass expires after `walkPeriodMs`: the next slice revokes cutover and re-runs the pass, which removes that row, bounding it like a folder's rolling walk (walk period + interval + pass time). Across a restart there is no residual: every startup walks every folder. #111 (the immediate retention of such a row) stays owner-accepted.
> - **Attempt lifetime.** A logical attempt spans `folder_membership_page_pending`, pressure and budget-partial yields; any other end retires that folder's cached membership digests when its next attempt starts, so a digest cached after its RPC settled cannot certify a later attempt. A yielded attempt's record is dropped when its folder leaves the inventory, so folder churn cannot grow it.
> - **Message events are detected by serial, never by timestamp.** Every "event since the work began" check (slice and lease assertions, the per-folder stale direction, scan sessions, proof records, pending clear) compares `_folderReconMutationSerial`, which both message-event handlers and exclusive membership changes bump. Two events can share a millisecond, so a `_lastSyncEventMs` comparison missed a re-add drained in the millisecond of an earlier event and let a ghost removal delete the live row (found in review, 2026-10-03). The per-folder stale direction binds its absence verdicts to the serial too: a re-add delivered after the verdict queues the message without a native write, so only the serial withholds the removal of the now-live owned row. `_lastSyncEventMs` remains only for the legacy quiet veto, quiet scheduling and telemetry.
> - **Quiet veto keyed on capability.** The five-second sync-quiet skip applies only when the native connection is not membership-capable. A capable helper keeps reconciling under sustained traffic and can earn cutover; exact proofs stay fenced on the membership epoch and the message-event serial. Known boundary (next train unit): a cold multi-page folder whose page time exceeds every gap between events still cannot complete its proof.
> - **Pending state is volatile.** The durable `fts_reconcile_pending` marker is replaced by a per-generation in-memory flag (true at init; cleared under the same conditions as before; re-set by every former marker site and by any pass that finds or repairs a deficit). A stored legacy key is removed once at init. The exclusive-operation marker retry subsystem is deleted: the post-release invalidation marks pending and wakes directly. Every startup still reconciles, so the durable marker carried no information.
> - **Outcome snapshot.** `fts_folder_recon_last` is written only when a non-read-only counter moved, or once when a completed pass has not yet been persisted as complete. The dirty flag clears only after a successful write of the same change serial. A no-change startup and an unchanged rolling walk write nothing.

> **2026-10-03 (PR 3, on the startup-walk main):** folder-scoped change evidence. A change in folder H never restarts, refuses or un-credits a proof about folder C (closes the owner-accepted O3 boundary: under sustained traffic a large folder's repair never converged).
>
> - **Native ledger by membership folderId.** `operationCoordinator.js` keeps, beside the unchanged global epoch, `folderId → post-bump epoch`, a wildcard epoch and an eviction floor (cap `FTS_MEMBERSHIP_LEDGER_CONFIG.changeLedgerCap`, 4096; eviction raises the floor and never grants validity). `ftsMembershipUnchangedSince(scope, since)` is the per-folder check; fences take an optional read `scope`. A mutation without scope is the wildcard; a throwing or partially committed mutation is still recorded; a fence records its inner wrappers' scopes and its own read scope when it ends.
> - **Only real folders are recorded.** Reconciliation registers its inventory (`registerFtsMembershipFolders`; the universe IS the latest inventory, never the history of every one — a grow-only union grew without bound under rename churn; a folder new to it, including one returning, is recorded as changed at registration, and a folder that left it has no proof left to protect). Engine wrappers pass descriptors `{ msgIds, folderIds }` resolved when the change is recorded: explicit owners always; a key is recorded for every REGISTERED folder whose key range holds it (the account is the text before the first `:`, account ids carry none; the coordinator indexes registered paths by account and tries only the `:` path ends no longer than that account's longest registered path, so a child key also touches a registered parent's raw range, and the work per key is bounded by the registered paths, never by the key's length); an unsplittable key is the wildcard; *(2026-10-04: keys are attributed only for a write that cannot name the owner it changed — a key-only removal, or an index sent in the legacy row shape; see the ADR-024 owner-known-writes amendment)*; before the first inventory no key is attributed (no proof exists yet, and registration records every folder as changed). Recording every syntactic candidate let colon-bearing Message-IDs in one hot folder fill the cap and void every older stamp; building every candidate identity was quadratic in the key's length (an every-account/path-pair enumeration measured ~74 MB for a 929-byte key, and one identity per `:` still ~51 MB for a 14k-character key). A key READ scope (`ftsMembershipUnchangedSince({ msgIds })`, the stale-owner fence) is never filtered by the universe: it matches the ledger's entries newer than the stamp against the keys' prefixes, so an explicit owner recorded before registration still breaks it; an undecodable recorded owner breaks it conservatively.
> - **Local ledger by folderKey** (`_noteFolderReconLocalChange`) replaces the global event serial (`_folderReconMutationSerial`) for per-folder checks. Its counter `_folderReconLocalSerial` is the message-event serial the global consumer (the pending clear) compares and the membership-state pass's row scopes are taken at, never `_lastSyncEventMs`: events can share a millisecond. Only a converted event (with `weFolderId`) names a folder; the experiment's fallback payload (server key + folder URI) is a change to every folder.
> - **Per-folder consumers use the folder's own evidence:** membership digests and their stamps, the local scan, the UID tier's digest and closing checks, the terminal digest reuse, the stale direction (loop, removal fence, and the absence verdicts' message-event binding: only an event naming the folder, or the wildcard, withholds a removal), the stale-cursor bind, memo commit fences, the session-done grant (native: the verified epoch in the folder's scope; local: no event in the folder, or the wildcard, since the operation started — 2026-10-04: a queued event is not the drain's alone, since a delete from `/F` and an add to `/F:Child` sharing one raw key coalesce into one add that drains against the row already indexed under `/F` with neither a native write nor a walk mark, so only the folder's own local proof records it; an event that queued nothing also marks the folder's walk obligation, which outlives the attempt; the tick-level global event check is gone), the fresh-proof guard, and the membership-state pass (2026-10-04: an ownerless row's verdict reads only its candidate folders, so only an event in one of them, or the wildcard, voids it; a voided row ends the page with the rows before it committed; the page's assignments commit before its removals, each assignment is re-checked against its row's candidate folders immediately before its batch commits, cutting the page at the first changed row, and a change during the commit marks those folders' walks; a removal is withheld by a folder event or by a message event in any folder whose key prefixes the removed key — listed in the inventory or not — since the inventory snapshot; scoped paging stops at the first positive). The pre-cutover metadata scan is deleted (2026-10-04, ADR-024). Global by meaning and unchanged: the pending-flag clear, the legacy orphan sweep and basis, the quiet veto, `_scheduleReconcileWhenQuiet`, telemetry. The migration slice's lease check no longer carries the global event check outside the state pass.
> - **A queued change stays the drain's (2026-10-04).** The session-done grant relies on every queued message change being processed as the LATEST intention for its key, or abandoned (abandonment marks the folder). Every drain writer acting on a captured entry is therefore compare-and-set on the entry's type and timestamp: abandonment already was; `_markResolveFailed`, the drain's retry-success reset and its dequeue after success now are too. Type matters as well as timestamp: a converted event can queue the opposite intention in the same millisecond. Before, a retry whose header read raced a removal wrote the captured add back over the newer delete, indexed it and dequeued it, and the folder completed with an orphan; a successful drain likewise dequeued a same-millisecond opposite intention queued during its own work. Marking a walk for every queued event was rejected: it would re-walk every busy folder after each event. *(2026-10-04, later: type + timestamp is not an identity — a removal and a same-type re-add can both land in the captured add's millisecond, and the old drain then dequeued the newer add. The compare-and-set is now on the captured entry object itself: every admission stores a new entry, and retry metadata (`_markResolveFailed`, the retry-success reset) is updated in place so the drain's capture stays the queued entry.)* *(2026-10-04, later still: processing the latest intention is not enough on its own — a delete from `/F` and an add to `/F:Child` sharing one raw key coalesce into one add that drains against the row already indexed under `/F` with neither a native write nor a walk mark. The grant therefore also checks the folder's own local proof since the operation started; see the per-folder consumers entry.)*
> - **The drain-quiet gate reads a queued update's own folder (2026-10-04).** A pending entry that names its folder (`folderKey`, set from the authoritative enqueue header) defers only that folder's attempt; the raw key prefix decides only for an entry with no folder. Before, a pending add in `/Cold:Hot` (raw key inside `/Cold`'s prefix) reported `/Cold` drain-busy and held its owed walk for as long as `/Cold:Hot` kept pending work (pre-existing on main). Legacy mode refuses prefix-overlapping folders as ambiguous before the gate, so the rule holds in both modes.

> **2026-10-04 (PR 3b, branch `agent/tb-recon-pr3b`):** corrections to the 2026-10-03 amendments above. The original text is kept as history; each statement below supersedes the one quoted. The membership side is in the ADR-024 PR 3b amendment.
>
> 1. **Reconnect re-walk:** "marks are serviced once migration re-earns cutover" → exact folder work needs only capability, so the marks are serviced by folder turns immediately; global cleanup no longer gates them.
> 2. **Walk obligations:** "manual clear" is no longer a producer (`clearPendingUpdates` and its engine route are deleted; it had no shipped sender). "Pending cannot clear while any entry remains" → there is no pending flag. Session completion is the orphan tail's quiet predicate `_folderReconQuietSince(generation, eventSerial)`: same generation, no message event since the serial, no walk obligation and an empty queue.
> 3. **Quiet veto:** "…and can earn cutover" → the global cleanup pass no longer gates exact folder work. It runs in alternating turns while incomplete and gates only orphan/session completion.
> 4. **Blessed residual:** "revokes cutover and re-runs the pass" → revokes global *cleanup* and re-runs the pass. Folder repair continues meanwhile.
> 5. **"Pending state is volatile"** is superseded: the volatile flag (`isReconcilePending`) is deleted with its only reader, the deferred startup maintenance tick (ADR-017 amendment). A changed outcome slice now resets `outcomes.complete`.
> 6. **"Message events are detected by serial":** "pending clear" is no longer a consumer. The serial is `_folderReconLocalSerial` (the name `_folderReconMutationSerial` above drifted when PR 3 replaced it). State-pass verdicts now also read a key-scoped local ledger beside the folder ledger (ADR-024 PR 3b).
> 7. **Queue persistence deleted (owner, 2026-10-04: "Whatever is simple and more robust is best").** The pending-update queue is no longer saved to `storage.local` or merged back at startup (`persistPendingUpdates`, `restorePendingUpdates` and the debounce timer are gone; the stored `fts_pending_updates` key is removed at init). Before, during the restore read a newer intention could be admitted and drained, and the older stored entry then overtook it. Intentions pending at shutdown are re-derived by the startup walk of every folder (missing and stale directions), never replayed. "Across a restart there is no residual" holds through the walk alone.

**Context:** Weekly scans in July/August 2026 repeatedly removed old ghosts from Gmail Bin even after ADR-020/021. The count design had two unsound assumptions: `getTotalMessages(false)` is cached state, and equal cardinality does not imply equal membership (one ghost plus one missing key cancels). A highest UID alone detects additions but not arbitrary deletions; HIGHESTMODSEQ detects change but also advances for flag-only changes and does not identify the changed UID.

**Decision:** Make reconciliation an exact, collision-resistant membership proof that is continuously and cooperatively scheduled after startup:

- `browser.accounts.list(true)` supplies the supported folder inventory; exact duplicate account/path identities are canonicalized once before folder scheduling and orphan evidence. `tmMsgNotify.getFolderState(accountId,path)` supplies `UIDVALIDITY` and HIGHESTMODSEQ telemetry. Local membership comes from an opaque `beginFolderMessageScan` / bounded `readFolderMessageScanPage` / `cancelFolderMessageScan` enumerator. For a previously verified IMAP folder with a nonzero unchanged UIDVALIDITY, the first scan requests msgKeys only and compares the UID count/digest plus a fresh native range fingerprint with the checkpoint; IMAP UID immutability then permits reuse of the prior exact Message-ID projection. Any UID/native/epoch change, unknown epoch, or non-IMAP folder takes the full scan. Full scans pre-encode each key once and cooperatively sort its UTF-8 bytes in SQLite `BINARY` order before hashing the exact de-duplicated `account:path:Message-ID` set; JavaScript UTF-16 order is not equivalent for supplementary-plane values. A UID-only result cannot enter repair or verification paths, and production never calls Thunderbird's one-shot `listAllKeys()`.
- Native helper ≥0.11.0 adds reader RPC `fingerprintMsgIdRange(startKey,endKey)` over ordered `message_ids` keys. It hashes each UTF-8 key as `u64be(length) || bytes`; no schema/reindex change.
- The legacy `account:path:Message-ID` key encoding is non-injective when one same-account folder path begins with another path plus `:`. Until the schema migration tracked by Thunderbird issue #20, every fresh inventory detects those overlap groups and fails every member closed: no per-folder range evidence/removal/verification or session completion, and no orphan proof globally because the summed ranges are not disjoint. The durable pending marker stays set, aggregate-only ambiguity counts are exposed, and retries use the normal cooperative error delay.
- `fts_folder_recon_memo` v3 migrates all v2 proof/backoff fields and adds restart-safe per-folder stale/missing cursors plus a durable round-robin folder cursor. `missingBackfillStarted=false` is the unambiguous before-first position; msgKey 0 is valid when the bit is true, while ambiguous zero cursors from v2/pre-release v3 migrate conservatively to before-first. A stale cursor is reusable only with the unchanged exact local set/key-map/UID proof and the exact native fingerprint under which it was earned; that binding fingerprint and the later targeted memo commit fence the same earned membership epoch, so intervening native writes cannot launder an advanced cursor. Backoff preserves the original pairing, while local drift and terminal mismatch clear it. A verified checkpoint is recorded only from a fresh local scan followed by a fresh native fingerprint after all repair and drain work.
- A timer processes at most one folder or orphan-basis slice per turn and keeps rescheduling until every folder and orphan prefix converges; there is no per-run or per-boot total-work cap. Later folders advance fairly through the durable round-robin cursor. A generation-owned hard-not-before floor reserves idle time at least equal to the preceding slice; shorter wakes cannot bypass it, and a raised floor re-arms an earlier timer later. Sync activity, active/waiting `SafeGetFull` work, chat typing, and a non-low pending queue pause scheduling without advancing cursors. Persistently failing folders use generation-local capped exponential deferral while other eligible folders progress. Every scheduler turn enumerates the exact current account tree once and passes that one inventory to its folder or orphan work; deleted/renamed identities are immediately pruned from every live dirty/drain/proof/backoff/snapshot set, with any discarded dirty proof forcing orphan work. An empty current inventory therefore runs orphan reconciliation with an empty known set instead of returning `no_folders`.
- One writer-preferred process-local operation coordinator owns full/smart/initial/maintenance/manual-cleanup/clear/reset/embedding scans and low-priority bounded reconciliation slices. Foreground work queues behind an exclusive owner, requests cancellation of active reconciliation, and writes/clears only its own runtime-session/run-id scan status. Owned progress writes are serialized per run; final clear closes that queue, drains earlier writes, and rejects later progress so status cannot be resurrected after release. Startup deterministically marks foreign/legacy active status interrupted. Reconciliation also owner-safely normalizes an ownerless active record after acquiring its mutually exclusive lease (covering a failed final status write); a genuinely live exclusive owner prevents that lease, and storage uncertainty still fails closed. Status is observability, not a TTL lock. Every email-membership `indexBatch`/`removeBatch`/`clear` attempt advances a serialized epoch even if its native call throws. An exclusive lease records its starting epoch and, after releasing ownership, coalesces any number of changed-epoch attempts into one notification; read-only leases emit none. The incremental listener synchronously discards all generation-local completion/backoff/orphan/active-proof evidence and dirties `__all__`. One private generation-owned owner then retries durable pending-marker persistence without limit at the normal error delay and arms ordinary scheduling only after a successful write; init, dispose, generation replacement, and runtime disable cancel its timer and stale await tail. A same-generation runtime re-enable re-arms retained exclusive `__all__` intent, reusing an already-successful in-flight marker write or retrying a failed one before wake. Reconciliation performs slow local/query, data-sized fingerprint, cooperative digest, and browser-storage work outside the membership mutex. Short fences only validate an earned epoch or contain bounded native mutation/verification; pre/post validation around storage refuses stale proof without blocking a foreground writer. A fence-owned opaque token prevents nested public mutators from deadlocking or double-advancing the epoch.
- Both `fts_folder_recon_memo` and `fts_reconcile_pending` use one permanent strict serialized storage chain across generations. Decisions read strictly; targeted synchronous patches re-read current state inside the chain and check generation before/after read and write. Old completions cannot overwrite new memo fields or remove a newer marker, and only fresh verification produced by the current run can make a folder session-done. Scan-status or reconciliation-storage read uncertainty fails closed and defers.
- Exactly one phase-tagged active-folder working proof may survive scheduler slices in an indexer generation: the scalar exact projection plus its one sorted `Uint32Array` msgKey view. It has no arbitrary entry, byte, or TTL cutoff and is not a multi-folder cache; memory is bounded by the one key array already inherently materialized for the current folder repair. The scheduler pins that owner across bounded missing slices and successful enqueue/drain handoffs, without holding the reconciliation lease while the foreground drain runs, so a finite large folder completes before the next folder and many-folder round robin cannot trigger cyclic rescans. Verification, topology/local invalidation, generation change, a real reconciliation error/post-verify backoff, a rejected incremental-drain await, or actual destructive abandonment releases/invalidate it so later healthy folders progress fairly. Drain failures use generation-local capped exponential deferral for only the affected folder(s), conservatively `__all__` when identity is unavailable; queued intentions and their durable marker remain retryable. Nothing is persisted and no Thunderbird objects, scan tokens, or Message-ID arrays are retained. The retained repair proof cannot write `verified`: equality forces a fresh full local scan followed by a fresh native fingerprint.
- A changed or unseeded folder always runs both stale and missing directions, including equal-count swaps. Stale native pages, global verify-then-remove rechecks, missing msgKey pages, and enqueues each have per-slice limits, but repeated slices are unbounded. The missing pass binary-pages through the sorted keys from the exact current header snapshot, avoiding a second parent-thread key walk. Missing additions enter only the existing incremental queue/drain and `SafeGetFull` body path.
- `_pendingUpdates` admits no new key above the configured high-water mark; overflow persists the folder as dirty and resumes reconciliation after the existing drain reaches low water. Every admitted record carries its explicit folder key. Any destructive/unverified abandonment (unparseable add/move, empty built header batch, stuck add/delete, manual clear) atomically persists the narrowest dirty marker before deleting the exact captured type/timestamp; marker failure retains the queue entry, while replacement/requeue and verified index/delete outcomes do not dirty. An abandoned row also invalidates its affected active proof before the folder enters capped fairness deferral. A thrown drain-level await retains and persists every captured or newer replacement intention, invalidates/defer its affected proof, and lets another eligible folder own the one working set; a never-settling foreground `SafeGetFull` remains governed by foreground pressure rather than an unsafe timeout. Marker writes and wakes coalesce during bursts, and an ensure racing an awaited marker removal serializes a restoring set after that removal. Restored legacy queues are capped and all affected folders are dirtied, so neither live nor serialized pending work can grow without bound.
- The Experiment's scan-token table is capped and wall-clock-idle swept; every page read refreshes the token, and `cancelFolderMessageScan`/shutdown closes it. A privileged getter exposes only `{live,maxLive,idleTtlMs}`. Extension status exposes bounded aggregate page/header, scheduler tick/slice/pressure/busy, elapsed/delay, max-pending, and accumulated outcome counters plus active-proof phase/key-size/reuse/release telemetry; it contains no account, folder, Message-ID, or subject values and resets with the indexer generation. Every persisted `fts_folder_recon_last*` snapshot is likewise aggregate-only: no notable-folder or unverified-identity arrays are stored. Persistent outcome snapshots accumulate bounded real slice outcomes, are throttled, and force a final completion write. `getFolderState` returns only identity/UID epoch/error state, not per-folder timing/log fields. Header enumeration, direct key lookup, and Message-ID probing share one fail-closed predicate that excludes both Thunderbird `IMAPDeleted` and `Expunged` rows from the proof domain.
- Non-IMAP folders have no stable UID contract but use the same exact, cooperatively paged local-header proof. Cancellation/foreground-pressure/local-mutation checks run after every parent page including the terminal page and at every encode/sort/merge/dedupe/frame/UID-hash boundary immediately before and after `crypto.digest`, so a newly waiting exclusive writer or foreground fetch preempts before later digest/native phases.
- Orphan-prefix evidence is staged from the exact current UTF-8 inventory digest, one fresh native count per disjoint folder range, the fresh known total, and a global native count/SHA under one unchanged membership epoch; it never compares live totals with frozen memo counts. Exact inventory drift restarts before-first. Once that basis is complete, benign membership growth does not discard forward page progress: each page is verify-before-remove under its own short mutation fence, without a repeated whole-index fingerprint. A terminal page takes fresh global evidence; any intervening native drift/removal starts a fresh bounded basis/pass so new orphans below the old cursor are caught.
- `runPostInitReconcile()` no longer performs the date-window `messages.query`, UID-cursor scan, or date-window FTS cleanup automatically. The fingerprint proof is date-independent and supersedes those automatic passes.
- Periodic hourly/daily/weekly/monthly alarms and the startup maintenance tick are retired and migrated off. Full Maintenance Scan / Full Reindex remain explicit user repair tools.
- Removal-event extraction now falls back to `folder.server.key`, carries `msgKey`, and rejects any partial `accountId`/folder/Message-ID key instead of queueing malformed deletes.

**Rationale:** A digest of actual membership answers the relevant question; counts and recent-UID watermarks do not. Thunderbird exposes lazy message enumeration but no bounded/ranged msgDB-key API: `listAllKeys()` materializes the whole table on the parent thread. The stable-IMAP UID tier avoids Message-ID access altogether on unchanged verified folders. When repair is required, reusing the single already-paged active proof for the missing-key view avoids that unbounded parent-thread call and reduces a large folder from repeated full scans to one initial full scan plus one mandatory fresh verification scan while its local generation is unchanged. Native range work stays on the helper's reader thread, body fetching stays behind the existing incremental drain, and cooperative yields plus an idle delay at least as long as the preceding scheduler slice cap consecutive reconciliation duty at 50%.

**Consequences:**

- “Guaranteed” means a SHA-256 collision-resistant equality proof of Thunderbird's synchronized local msgDB versus native FTS, not a mathematical proof and not a direct unsynchronized server query.
- Existing v2 checkpoints migrate to v3 without losing equality or backoff evidence; ambiguous zero missing cursors replay key 0, while nonzero cursors become explicitly started. No durable key array is persisted. The next exact snapshot establishes any new progress fields.
- Worker suspension discards the active working proof and live scan token. Restart re-enumerates local headers and validates the durable v3 cursor against the new UIDVALIDITY/key-map proof before resuming, so memory reuse is only a performance optimization.
- Flag-only changes do not cause work because the UID digest is authoritative; HIGHESTMODSEQ is diagnostic only.
- Very large repairs are split across repeated slices and converge in the same live session when pressure permits. The startup pending marker remains until a clean post-drain proof, but a restart or MV3 worker suspension resumes conservatively from persisted cursors rather than depending on an in-memory iterator.
- Fresh account inventory is deliberately re-enumerated once per scheduler turn; there is no cross-turn inventory cache. Strict targeted memo transactions still read/clone the monolithic per-folder memo, so completing `F` folders retains a known Θ(`F²`) aggregate storage-serialization cost. That is an accepted residual for this revision, separate from the removed repeated parent-header scans.
- Foreground writers may wait briefly for a bounded reconciliation fence, never for a long local scan. Conversely, a pending writer cancels reconciliation at its next page/query/yield boundary. Native membership mutations that race proof construction invalidate the epoch and refuse cursor/memo acceptance rather than laundering the newer state into older evidence.
- ADR-020 cursor-store/heartbeat and ADR-016 watermark helpers remain for compatibility/tests, but no longer drive the automatic startup path. The obsolete privileged `listKeysAboveKey` API and its one-shot `listAllKeys()` implementation are removed; the retained test-exported cursor walker can only consume the bounded scan-token pages. ADR-021's verify-then-remove, resumable missing scan, and orphan safeguards are retained after the trigger changes.
