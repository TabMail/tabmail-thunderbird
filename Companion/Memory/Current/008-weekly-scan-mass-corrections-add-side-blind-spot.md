- **Data pattern:** 06/29 weekly scan corrected 354 (352 indexed, 2 removed) — ALL account3 `[Gmail]/All Mail`, `Sent Mail`, `Spam`, `Bin` (ZERO account3 INBOX entries), message Dates spanning exactly 06/17–06/23, nothing newer. Sent corrections carry Gmail-client Message-IDs (`CAORVca…@mail.gmail.com`) → mail was sent/filed from other clients that week. 07/01 scan corrected 1 (a recent INBOX arrival) — separate, minor (single mid-session event miss).
- **Mechanism (the 2026-06-10 "mirror gap on the add side", now proven systematic — not just forged-Date spam):** INBOX indexed live all week (TB running), but TB syncs Gmail secondary folders lazily/in bulk. When their catch-up finally landed (folder opened / boot-time full sync), the headers entered the local msgDB either during the **addon-load pre-listener window** (the MFN listener registers only after `initFtsEngine` → native-host handshake → `initIncrementalIndexer`, i.e. seconds-to-45s+ after TB already started syncing) or via a bulk sync that fired no per-hdr events. Boot reconcile Phase 1 cannot recover them: `messages.query({fromDate: watermark.completedAtMs − 1d})` keys on the **message Date header**, and the heartbeat + intervening clean reconciles had already advanced `completedAtMs` to "now" — so messages dated 06/17–06/23 fell permanently outside every subsequent boot window. Only the weekly scan's 3-week reach recovered them (up to ~7-day search outage per message).
- **Core invariant violated:** the watermark claims "FTS verified consistent with IMAP for dates ≥ fromMs", but Phase 1 only verifies against the **local msgDB snapshot** — for lazily-synced folders the msgDB itself isn't yet consistent with the server when the watermark advances. Same arrival-time-vs-Date-header decorrelation as the iOS "IMAP sync windows by UID, NEVER date" rule (ADR-IOS-042).
