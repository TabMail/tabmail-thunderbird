- **`tmWebFetch` — KEEP** (an earlier verdict of "REPLACEABLE/eliminate" was WRONG; corrected after web research + reading the code). Two documented reasons make it more than a CORS shim: (1) **CORS bypass for ARBITRARY URLs** — `web_read.js:79` ("bypasses CORS"); `web_read` fetches whatever URL the agent picks, so it needs `<all_urls>`, which in MV3 Firefox/Thunderbird is **optional/user-revocable** (granted at install FF127+, but revocable ad-hoc) and has a history of background-fetch CORS regressions; the experiment's system principal is unconditional. (2) **Rich network error diagnostics** — `describeNetworkError()` in `tmWebFetch.sys.mjs` maps XPCOM/NSS codes to human-readable failures (DNS/cert/refused/timeout/redirect-loop) and *resolves* (not rejects) so they survive the privileged→WebExtension boundary; stock `fetch` only yields opaque "Failed to fetch", bad for an agent tool that must explain *why* a read failed. NOTE: `web_read` is an ATN review hotspot either way (system-principal arbitrary fetch OR `<all_urls>`), so replacing the experiment wouldn't reduce scrutiny.
- **`glodaSearch` — LIVE, keep (replaceable only as a Phase-2 project).** NOT replaced by native FTS — they do orthogonal jobs. **Native FTS** (`connectNative("tabmail_fts")`) = keyword/semantic search → `email_search` tool. **gloda** = cross-folder conversation membership → (a) the **related-messages bubble** (`threadConversation.js:283`, default-on, fires per message view — this is the feature kept *instead of* the abandoned card-reorder) and (b) thread-level action-tag aggregation (`threadTagGroup.js:214`, live in message processing).
  - **Why FTS can't do the bubble:** the native index (`tabmail-native-fts/src/fts/db.rs`) stores `msgId/subject/from/to/cc/bcc/body/dateMs/hasAttachments` — NO `References`/`In-Reply-To`/`threadId`; `fts/indexer.js buildBatchHeader` doesn't even extract those headers. FTS answers "contains these words", the bubble needs "belongs to this conversation" — orthogonal. So FTS is structurally incapable as built.
  - **The gloda-free path (proven on iOS, NOT yet in TB):** iOS has no gloda — it does References-chain reconstruction. Stores `rfc822MessageId`+`inReplyTo`+`messageReference` junction+`computedThreadId` (GRDB v13/v26/v27); `ThreadDetection.findRelatedMessages` BFS-walks Message-ID links (depth≤5) then dedupes **cross-folder by RFC-822 Message-ID**. To drop gloda in TB: extract+store References at index time → junction index (native-FTS new schema/RPC, or addon IDB) → chain-walk + per-folder `messages.query({headerMessageId})` aggregation (that primitive already exists, used in `onMoved.js`). Must replace BOTH consumers (bubble + `threadTagGroup`). The per-folder `nsIMsgThread` route (the dead `threadMessages` experiment) is folder-scoped only → loses Sent/All-Mail copies → do NOT use it as the replacement. Net: a real "kill glodaSearch + gain iOS parity" project, not a quick delete.
