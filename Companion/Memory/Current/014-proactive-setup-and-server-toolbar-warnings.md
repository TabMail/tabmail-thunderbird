# Proactive setup + server toolbar warnings (issue #12)

- **Goal:** the `setup` and `server` red-dot keys used to be popup-reported only (went stale until the popup was reopened). Now the background maintains them proactively. **Zero added backend requests** ("no hammering").
- **Shared checks (`agent/modules/setupChecks.js`):** `checkPlaintextComposition` / `checkDefaultCalendar` / `checkDefaultAddressBook` / `checkSetupConfiguration` were MOVED out of `popup/popup.js` into this module, imported by BOTH popup and `chat/background.js`. **This is mandatory, not cosmetic:** if the two contexts computed the warning differently, the dot would flip every time the popup opened/closed. `forceAllIdentitiesPlaintext` (the "[Click to fix]" action) stays popup-only.
- **`setup` wiring (`chat/background.js syncSetupWarning()`):** evaluated at startup (top-level so it re-runs on every background wake), on `storage.onChanged` for `defaultCalendarId`/`defaultAddressBookId`, and on `accounts.onCreated/onDeleted` + `identities.onCreated/onDeleted/onUpdated` (feature-detected, non-async per TB rule 4). On error it clears the dot (mirrors the popup's `updateSetupWarning` catch — "don't nag on error"). **Accepted limitation:** the per-identity `compose_html` pref has NO WebExtension change event, so flipping plaintext directly in TB's Account Settings won't update the dot until the next popup open / identity event / startup (self-heals; same as old behavior). All inputs are local → no network.
- **`server` wiring — PASSIVE, storage-relayed:** `agent/modules/llm.js` derives backend health as a side-effect of real completions traffic (`noteServerHealth(healthy)` writes `storage.local.tabmailServerHealthy`, deduped via `_lastNotedServerHealthy`). **Why storage, not `setWarning` directly:** `llm.js` runs in the chat/compose/config contexts, NOT the background — calling `setWarning` there would mutate a *different* `icon.js` module instance and clobber the toolbar. The background owns `setWarning("server")` via a `storage.onChanged` + startup read of `tabmailServerHealthy` (same pattern as `consent`). The popup's `showServerStatusWarning` also writes this key.
- **Health classification (the correctness bit):** healthy=true on 200 / non-auth 4xx / 401-403 auth (server *responded* → reachable); healthy=false ONLY on 5xx or a fetch that never produced a response (network error / connect-timeout). **Deliberately does NOT flip on 401/403/429** so quota-exhausted / rate-limited users don't see a false "server down" dot. User-initiated aborts (external `abortSignal`) are excluded (not an outage). Idle clients get no passive signal by design (no usage → no user-visible impact; popup's on-open `GET /health` remains the immediate check).
- **Tests:** `test/setupChecks.test.js` (13) + `test/serverHealthSignal.test.js` (7, drives real `sendChatCompletions` with `_internal_no_retry=true`, pins the classification incl. the 401-is-reachable and user-abort cases). `_testExports` gained `noteServerHealth` + `_resetServerHealthSignal`.
