# Search tool sessions belong to the chat turn or to one headless run

Recorded 2026-10-28 (#171).

- **What a session is.** `memory_search`, `email_search`, `inbox_read` and `calendar_search` (and `calendar_read`, which delegates to it) keep what they fetched for each set of arguments, so the next `page_index` of the same call comes from the same results instead of a fresh fetch that may have shifted.
- **Where they live (`chat/modules/toolSessions.js`, `createToolSessions`).** The chat window's turn has one set per tool; `resetToolPaginationSessions` (core.js), called by `processUserInput` at each new user turn, clears it through each tool's `resetPaginationSessions` (`resetTurn`). Each headless run has its own set, kept in a `WeakMap` under the run's isolated context (`createIsolatedContext()`), which `executeToolsHeadless` passes to every tool as `options.headlessRun`. A batch with no context gets a fresh store of its own.
- **Why per run, not a reset at run start.** Before #171, headless runs used the turn's module-level sets and nothing ever reset them in the background, so a check-in, reply or compose run repeating an earlier run's call was served the earlier run's results (missing newer memory, mail, inbox and events) until the background restarted. Headless runs overlap (reply generations run alongside each other and check-ins, which is why each already has its own ID context), so a reset at each run's start would clear another run's pages mid-run and could still hand a run results fetched before it started. Scoping by the run's context gives each run its own snapshot, keeps paging within a run, and leaves the chat turn alone.
- **When adding a tool with sessions:** create them with `createToolSessions()`, read them with `sessions.of(options.headlessRun)` inside `run`, and clear them in `resetPaginationSessions` with `resetTurn()`. A wrapper that calls another tool must forward its `options`.
