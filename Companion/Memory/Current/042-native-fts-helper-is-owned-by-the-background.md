# The native FTS helper is owned by the background; other pages ask it

Recorded 2026-10-04. Found in the tier-1 review of `inbox_read` attachment flags (TB PR #123), then fixed for every caller.

- **Each extension page has its own copy of every module.** The chat window (`chat/chat.html`), compose and settings pages import `fts/engine.js` / `fts/nativeEngine.js` as separate module instances from the background (memory 014). Only the background's `chat/background.js` runs `initFtsEngine()`, so only its copy holds the helper's port.
- **A call from a page used to start a second helper.** `nativeRPC` → `ensureConnected` → `initNativeFts` → `runtime.connectNative("tabmail_fts")` in the page's copy. Firefox creates one `NativeApp` (one helper process) per connecting context and ties it to that page (`NativeApp` in `NativeMessaging.sys.mjs`; MDN `runtime.connectNative`: the app runs until the page that created the port is destroyed). The second process ran hello (including the self-update check and its CDN fetch), init, profile detection, migration and the embedding-model load, and it could write to the same database outside the background helper's ordering.
- **Paths that did this before 2026-10-04:**
  - `safeGetFull`'s index step (`_getFtsSearch` → `ftsSearch.getMessageByMsgId`, and `ftsSearch.stats()` in its miss diagnostics). Reached from chat `email_read` and compose.
  - #123's first draft of `_getAttachmentFlags` (fixed before merge).
- **The rule now, enforced in `fts/nativeEngine.js`:**
  - `initNativeFts()` marks this context as the owner (`ownsNativeHelper()`). Only `initFtsEngine` calls it.
  - `ensureConnected` and `recheckAvailability` refuse to connect in a context that is not the owner, so an RPC there rejects with "Native FTS helper not connected" and never spawns a process.
  - With "use FTS search" off, the background never calls `initFtsEngine`, so no context owns the helper and nothing starts one (before, a `safeGetFull` call connected it lazily).
- **How a caller reaches the index:** `ftsRequest(cmd, fields, direct)` in `fts/ftsRequest.js`. In the owner it calls `direct({ ftsSearch, memorySearch })`. Anywhere else it sends `{type: "fts", cmd, ...fields}` to the background, whose `attachCommandInterface` handler answers: undefined when nothing handled it (the background has not attached the handler yet: startup or hot-reload race), `{error}` when the command threw. Since #175 (2026-10-28) `initFtsEngine` attaches the handler before it connects the helper, so a page's request gets what a direct call in the background gets: it waits while the helper connects, and gets "Native FTS helper not connected" at once while the helper is missing (before, the handler attached only after the helper connected, so a page waited out its 30 s readiness loop, and a page that does not retry, such as "Clear chat history" or the memory size limit, read the silence as success). Test: `test/ftsHelperDownAnswers.test.js`. Callers: `safeGetFull` (`getMessageByMsgId`, `stats`), `inboxContext._getAttachmentFlags` (`getAttachmentFlags`), `email_search` (`search`, #170), `memory_search` (`requestMemory`, `memorySearch`) and `memory_read` (`listWindow`, `readWhole`; `memorySearch`, `memoryRead`) since #155.
- **Before adding an index read or write:** call it through `ftsRequest` unless the code only ever runs in the background. A new `cmd` needs a case in `attachCommandInterface`.
- Tests: `test/nativeHelperOwnership.test.js` (no connect from a non-owner, owner connects, `ftsRequest` both ways), `test/getFullCacheCleanup.test.js` ("outside the context that owns the native helper"), `test/inboxContextAttachments.test.js`.
- Not every module caller needs `ftsRequest`: `indexChatSession` (`fts/memoryIndexer.js`) is reached only from `_kbUpdateImpl` (`kbUpdate`, in the background on `kb-update-from-window-close`), so its direct call runs in the owner. `periodicKbUpdate`, which does run in the chat window, indexes turns through `indexChatTurn`, already a runtime message. Corrected in tier-1 review, 2026-10-04.
- **The background cannot message itself (#155, 2026-10-28).** `runtime.sendMessage` is not delivered to the frame that sent it (MDN), so a raw `{type: "fts"}` message from the background never reaches its own `attachCommandInterface` handler: it rejects ("Could not establish connection. Receiving end does not exist.") when no other extension page is open, and resolves undefined when one is open but does not answer. Chat tools also run in the background, through `executeToolsHeadless` (proactive check-in task evaluation, `createReply`, compose edits started from `compose/background.js`), so a tool that sends a raw FTS message works in the chat window and fails in a headless run. `memory_search` waited out its 30 s readiness loop and failed with "invalid response format"; `memory_read` failed at once. Both now go through `ftsRequest`; in the owner `memory_search`'s closure turns a thrown helper error into the same `{error}` the handler gives a page. Reproduced and verified on Thunderbird Beta 158 headless via Marionette: the probe is added to a throwaway copy's manifest `background.scripts` (Marionette's chrome context cannot reach the out-of-process background page) and reports through an extension tab's title (`tabmail.tabInfo[].browser.contentTitle`). Test: `test/memoryToolsContext.test.js` (TB-196). `email_search` had the same defect in headless runs (#170: waited 30 s, then "fts search failed: invalid response format", on Beta 158) and now goes through `ftsRequest` the same way, its owner path calling `ftsSearch.search(q, { from, to, limit, ignoreDate, sort })` exactly as the handler's `search` case does (TB-198, `test/emailSearchContext.test.js`). Headless runs also used to share the chat turn's search sessions, which the background never reset, so a later run could be served an earlier run's answer; since #171 each headless run has its own (memory 047).
- **Test-harness quirk:** importing `fts/ftsRequest.js` loads the real `fts/nativeEngine.js`, which loads `agent/modules/config.js`, which reads `browser.storage.onChanged` at import; a page-context test needs a `storage` stub. A `vi.mock` of `nativeEngine.js` did not hold here: concurrent dynamic imports (`readWhole`'s `Promise.all`) loaded the real module.
