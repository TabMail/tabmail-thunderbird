# Thunderbird's MessageHeader has no attachment field

Recorded 2026-10-04 after an attachment-only email (a PDF, no body text) was reported by the chat agent's `email_read` as `has_attachments: no`. Rewritten the same day when the index was fixed (second commit of the PR), and again when new rows switched to the downloaded MIME tree and the repair became per account (third commit).

- **The WebExtension `MessageHeader` type has no `hasAttachments` property.** Thunderbird 157's `messages.json` schema and the `convert` in `ExtensionMessages.sys.mjs` expose no attachment field, so `header.hasAttachments` is always `undefined` and `Boolean(header.hasAttachments)` is always `false`. Nothing errors. Before this fix, four places read it: `email_read`, `inboxContext` (feeds `inbox_read` and the inbox prompt context), `email_search` (through the index column), and `fts/indexer.js`, so every FTS row said "no attachments".
- **The database flag is a heuristic — owner-accepted 2026-10-04 for old rows and unindexed mail.** `nsMsgMessageFlags.Attachment` (`0x10000000`) is the paperclip flag. Thunderbird sets it when the header is parsed (`nsParseMailbox.cpp` / `MailHeaderParsing.cpp`), only for a top-level `multipart/mixed` Content-Type. It was measured on the reported message: flags `0x10000081` in its IMAP folder's `.msf` (the paperclip was right; our reader was wrong). Known misses: a single-part attachment email (the whole body is the file) reads "no", and a `multipart/mixed` with no file reads "yes".
- **Only the message reader corrects the flag.** `msgHdrView.js` calls `markHasAttachments(...)` when a message is displayed, in both directions, ignoring vCards and PGP keys. `messages.getFull()` (which the indexer uses) never touches it. Gloda (`GlodaFundAttr.sys.mjs`) only clears a wrong "yes", and only for offline or local messages. So indexing does not fix the flag (checked in comm-central source 2026-10-04).
- **The exact MV3 answers are too expensive for flags (owner 2026-10-04).** `messages.query({attachment})` and `messages.listAttachments` both run a full MIME parse per message (`getAttachmentParts`), which can download the message. Do not use either for attachment flags.
- **The MIME tree the indexer already downloads is exact (owner 2026-10-04: "way more robust").** `getFull()` sets `MessagePart.name` exactly on the parts Thunderbird treats as attachments, `""` when the file has no name (`ext-messages.js` `convertMessagePart`). `agent/modules/attachmentParts.js`: `listAttachmentsFromFull(full, header)` collects named parts without descending into a named part (an attached email is one file) and returns null when the tree cannot tell — a synthetic FTS body, `header.headersOnly` (getFull drops a Partial message's parts), or `decryptionStatus === "fail"` (getFull drops the parts). `hasPaperclipAttachment` applies Thunderbird's reader rule: `text/vcard`, `text/x-vcard`, `application/pgp-keys` do not count.
- **`tmHdr.getHasAttachmentBulk(messageIds)` reads the flag by WebExtension id.** It uses `context.extension.messageManager.get(id)`, an exact O(1) lookup that returns null for a gone, IMAP-deleted or expunged message, and returns `true`/`false`/`null` per id, in order. A WebExtension id is not a msgKey. Until 2026-10-04 the replied/HasRe reads (`getRepliedBulk`, `getHasReBulk`, `getReplied`, `getFlags`, and `getMsgKey`) passed the WebExtension id to `folder.GetMessageHeader` as a msgKey. When no message in the folder had that key they fell back to a Message-ID search and got the right message; when one did, they read that other message's flag (a reply pill turned to none, or stayed on a replied email). They now take WebExtension ids and use `messageManager.get(id)`; the folder and Message-ID lookups were deleted.
- **New rows are exact.** `buildBatchHeader` reads the flag for each batch (a non-boolean flag skips the message, leaving it pending or, in the drain, handing it to reconciliation; a failed or misaligned read throws, so the batch fails or stays queued). `populateBatchBody` then overwrites it with the MIME-tree answer whenever `listAttachmentsFromFull` can tell. Both the full scan and the incremental drain go through these two functions.
- **Old rows: a per-account repair with the flag.**
  - The native `indexBatch` is `INSERT OR IGNORE`, so the repair cannot update a row in place. `readdStaleAttachmentRows` takes the membership epoch, reads each already-indexed message whose flag is `true` but whose stored row says 0, then inside one `withFtsMembershipFence(epoch, …, { mutation: true })` removes those rows and re-adds them from their stored copy (body, headers, ICS, date) plus `hasAttachments: true` and the current `folderId`. Any membership change that completes after the epoch was taken makes the fence throw; the batch counts as failed. (The first version also held the membership read mutex during the reads; the epoch check already covers it, so it was deleted.)
  - Only a full run (`indexMessages` without a date range) repairs, and only in accounts not yet recorded. `iterAllFolders` reports each account as complete or not (`getAllFoldersForAccount(accountId, onError)` now reports a folder it could not list, and an account its own lookup cannot find). An account is recorded in storage.local `fts_attachment_repaired_accounts` (`fts/attachmentFlags.js`) when it was complete and none of its repair batches failed. A run that throws records nothing.
  - Per account because on a cold start `accounts.list()` can leave whole accounts out for 30+ minutes (memory 033); a global marker set after such a run made email_search trust stale 0 flags for the missing accounts forever (review round 2, 2026-10-04).
  - `fts/engine.js` starts `_runSmartReindex(false)` in the background at engine init when `fts_initial_scan_complete` is set and any listed account with a root folder is unrecorded, so the repair re-runs at each startup until every loaded account is recorded. The settings-page smart reindex goes through the same function.
  - Known, rare: in an account not yet recorded, a row indexed exactly as "no" whose flag says "yes" (a `multipart/mixed` with no file) is flipped to "yes" by the repair — the flag's own answer, the same as an old row.
  - The superseded global marker `fts_attachment_flags_repaired` (de894f74, never released) is no longer read.
- **File names are indexed for new rows (2026-10-04, tabmail-native-fts ADR-NF-005).** `populateBatchBody` sets `row.attachmentNames = attachmentNamesText(attachments)` from the same MIME-tree list: one named file per line; a name written as one run (`TaxReceipt2024.pdf`) is followed by its words split at case and letter/digit changes, because the FTS tokenizer splits only at spaces and punctuation. The native helper stores them in its own shard column (no capability gate: an older helper ignores the field). `readdStaleAttachmentRows` carries `stored.attachmentNames` through the remove-and-re-add, and sends the re-add even when the remove call fails: the helper's writer can be busy converting a shard (ADR-NF-005), so a timed-out remove still runs later, in order, and without the re-add the rows would stay deleted until the next run. **No backfill (owner):** rows indexed earlier keep an empty column until a full reindex; a smart reindex does not fill them, because `filterNewMessages` skips indexed rows before any download and the flag repair re-adds from the stored copy. A synthetic (FTS-served) body gives no names.
- **Where each reader gets attachments now:**
  - `email_search` uses the index column (`Boolean(hit.hasAttachments)`) for hits whose account (the msgId prefix before the first `:`, `accountIdOfMsgId`) is recorded. For the others it resolves each hit with `resolveUniqueMessageKey` (colon-safe, fail-closed) and asks `getHasAttachmentBulk` by id. If the recorded set cannot be read, it asks for every hit.
  - `inboxContext` (feeds `inbox_read`) reads the index column for emails whose account is recorded, in one native call: `getAttachmentFlags(msgIds)` (tabmail-native-fts, 2026-10-04) returns `hasAttachments` per msgId, or null for one not indexed. Thunderbird's `getHasAttachmentBulk` by id answers only the emails still null: those not indexed, those in unrecorded accounts, and every email when the recorded set or the native call fails. A helper too old to know the method answers "Unknown reader method", which lands in that last case. Before this, `inboxContext` asked `getHasAttachmentBulk` for every email, because the only index read was `getMessageByMsgId`, one round trip per message carrying the full body.
  - `email_read` uses `listAttachmentsFromFull` on the tree it already fetched, lists every file after the body in iOS's format (`  - name (contentType, size bytes)`, `(unnamed)` for `""`), and says `has_attachments` by `hasPaperclipAttachment`. When the tree cannot tell, it uses the DB flag by id and prints no list.
  - A flag that cannot be read prints `has_attachments: unknown`, never `no` (`formatMailList`, `email_read`).
- **`safeGetFull` cannot answer "has attachments".** Its native-FTS tier returns a synthetic message, so anything that walks `full.parts` sees no parts on an FTS hit. The `email_read` ICS scan had the same gap on FTS hits until 2026-10-04: the synthetic message now carries the row's stored `parsedIcsAttachments` (the indexer parses invites when it downloads a message; native `message_meta`), `email_read` prints that text instead of scanning parts, and `populateBatchBody`'s synthetic branch re-adds it rather than `""`.

Before reading any field of a WebExtension type, check Thunderbird's schema for it. A missing field reads as `undefined` and coerces to a plausible default.

## Superseded: the first commit's design (kept for history)

The PR's first commit (`4e320bf1`) had `email_read` call `browser.messages.listAttachments(weId)`, and `inboxContext`/`email_search` call `getHasAttachmentBulk(items)` keyed by Message-ID only. `email_search` matched keys with `getUniqueMessageKeyCandidates`, and the FTS column was left at 0 and unread. The owner rejected the second Thunderbird read on every search ("fix the indexer… rely on our indexing"), and rejected `listAttachments`/`query` as too expensive. That smoke test (PDF read via `listAttachments`) was reported working.
