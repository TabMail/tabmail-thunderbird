# Thunderbird's MessageHeader has no attachment field

Recorded 2026-10-04 after an attachment-only email (a PDF, no body text) was reported by the chat agent's `email_read` as `has_attachments: no`. Rewritten the same day when the index was fixed (second commit of the PR).

- **The WebExtension `MessageHeader` type has no `hasAttachments` property.** Thunderbird 157's `messages.json` schema and the `convert` in `ExtensionMessages.sys.mjs` expose no attachment field, so `header.hasAttachments` is always `undefined` and `Boolean(header.hasAttachments)` is always `false`. Nothing errors. Before this fix, four places read it: `email_read`, `inboxContext` (feeds `inbox_read` and the inbox prompt context), `email_search` (through the index column), and `fts/indexer.js`, so every FTS row said "no attachments".
- **The database flag is a heuristic — owner-accepted 2026-10-04.** `nsMsgMessageFlags.Attachment` (`0x10000000`) is the paperclip flag. Thunderbird sets it when the header is parsed, only for a top-level `multipart/mixed` Content-Type, and corrects it when the message is displayed. It was measured on the reported message: flags `0x10000081` in its IMAP folder's `.msf`. Known misses, accepted by the owner: a single-part attachment email (the whole body is the file) reads "no" until it is opened, and a `multipart/mixed` with no file reads "yes". The owner chose this flag over an exact MIME answer.
- **The exact MV3 answers are too expensive for flags (owner 2026-10-04).** `messages.query({attachment})` and `messages.listAttachments` both run a full MIME parse per message (`getAttachmentParts`), which can download the message. Do not use either for attachment flags.
- **`tmHdr.getHasAttachmentBulk(messageIds)` reads the flag by WebExtension id.** It uses `context.extension.messageManager.get(id)`, which is an exact O(1) lookup and returns null for a gone, IMAP-deleted or expunged message. It returns `true`/`false`/`null` per id, in order. A WebExtension id is not a msgKey. The `getRepliedBulk`/`getHasReBulk` items still pass `key: msg.id` as a msgKey, which is a known wrong-message hazard left for a follow-up.
- **The index stores the flag, and a one-time repair fixes old rows.**
  - `fts/indexer.js` `buildBatchHeader` reads the flags for each batch. A message whose flag is not boolean is skipped, which leaves it pending for the next scan. A failed or misaligned read throws, so the batch fails.
  - The native `indexBatch` is `INSERT OR IGNORE`, so the repair cannot update a row in place. `readdStaleAttachmentRows` reads each already-indexed message whose flag is now `true` but whose stored row says 0. Inside one `withFtsMembershipFence` (mutation), it removes those rows and re-adds them from their stored copy (body, headers, ICS, date) plus `hasAttachments: true` and the current `folderId`. If the membership epoch changed, the fence throws and the batch counts as failed.
  - Only a full smart reindex (`indexMessages` without a date range) repairs. If it finishes with no failed batch and no traversal error, it sets the storage.local marker `fts_attachment_flags_repaired` (`fts/attachmentFlags.js`). A date-range scan neither repairs nor marks.
  - `fts/engine.js` starts `_runSmartReindex(false)` in the background at engine init whenever `fts_initial_scan_complete` is set and the marker is not. So the repair re-runs at each startup until one run succeeds. The settings-page smart reindex goes through the same function.
- **Where each reader gets attachments now:**
  - `email_search` uses the index column (`Boolean(hit.hasAttachments)`) once the marker is set. Before that, it resolves each hit with `resolveUniqueMessageKey` (colon-safe, fail-closed) and asks `getHasAttachmentBulk` by id.
  - `inboxContext` (feeds `inbox_read`) asks `getHasAttachmentBulk` by id.
  - `email_read` derives the attachments from the `getFull` MIME tree it already fetched: parts with a `name` are files, and it does not descend into a named part, so a forwarded `.eml` counts once. That answer is exact and costs nothing. When `safeGetFull` answered from the FTS index (`__tmSynthetic`, `parts: []`), it falls back to the DB flag by id. It lists the files after the body in iOS's format (`  - name (contentType, size bytes)`).
  - A flag that cannot be read prints `has_attachments: unknown`, never `no` (`formatMailList`, `email_read`).
- **`safeGetFull` cannot answer "has attachments".** Its native-FTS tier returns a synthetic message, so anything that walks `full.parts` sees no parts on an FTS hit. The `email_read` ICS scan has the same gap on FTS hits (follow-up).

Before reading any field of a WebExtension type, check Thunderbird's schema for it. A missing field reads as `undefined` and coerces to a plausible default.

## Superseded: the first commit's design (kept for history)

The PR's first commit (`4e320bf1`) had `email_read` call `browser.messages.listAttachments(weId)`, and `inboxContext`/`email_search` call `getHasAttachmentBulk(items)` keyed by Message-ID only. `email_search` matched keys with `getUniqueMessageKeyCandidates`, and the FTS column was left at 0 and unread. The owner rejected the second Thunderbird read on every search ("fix the indexer… rely on our indexing"), and rejected `listAttachments`/`query` as too expensive. That smoke test (PDF read via `listAttachments`) was reported working.
